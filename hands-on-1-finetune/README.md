# Hands-on 1 — Fine-tuning Local LLMs

**Bài 1 — Tinh chỉnh mô hình ngôn ngữ cục bộ** · [English below](#english)

## Tiếng Việt

### Bạn sẽ làm gì

Lấy một mô hình mở nhỏ (**Qwen2.5-1.5B-Instruct**) và dạy nó trở thành
**Aurora** — trợ lý kỹ thuật của công ty (hư cấu) Aurora Grid Systems — chỉ trong
vài phút trên GPU của RTX Spark. Sau đó đặt câu hỏi cho cả mô hình gốc và mô hình
đã tinh chỉnh, và so sánh song song.

```
dữ liệu (86 ví dụ) ──▶ LoRA trên GPU ──▶ gộp + GGUF ──▶ Ollama ──▶ so sánh trước / sau
```

### Các khái niệm chính

- **LoRA** không sửa 1,5 tỷ tham số của mô hình. Nó gắn thêm các ma trận nhỏ (khoảng
  1% số tham số) và chỉ huấn luyện phần đó. Nhanh, tốn ít bộ nhớ, và mô hình gốc
  vẫn nguyên vẹn.
- **Chỉ học phần trả lời.** Mỗi ví dụ là một đoạn hội thoại; mô hình chỉ bị chấm
  điểm trên câu trả lời của trợ lý, không phải trên câu hỏi.
- **GGUF** là định dạng tệp mô hình mà Ollama (và llama.cpp) dùng để chạy.
  Sau khi huấn luyện, LoRA được gộp vào trọng số rồi chuyển sang GGUF.

### Các bước

1. Mở tab **1 · Tinh chỉnh** trong ứng dụng workshop.
2. Xem **Dữ liệu huấn luyện**: danh tính ("Tôi là Aurora…"), định dạng trả lời có
   chữ ký, cách từ chối câu hỏi ngoài phạm vi, và vài thông số sản phẩm.
   Tệp gốc: `data/train.jsonl` (được tạo bởi `data/build_dataset.py`).
3. Bấm **Bắt đầu tinh chỉnh**. Theo dõi đường **loss** giảm dần theo từng bước.
4. Khi thấy "Xong", dùng phần **Trước và sau khi tinh chỉnh**: bấm các câu hỏi mẫu.
   Các câu này được diễn đạt **khác** với dữ liệu huấn luyện.

### Điều cần để ý

- Cả hai mô hình nhận **cùng một system prompt**, trong đó ghi rõ "You are Qwen,
  created by Alibaba Cloud". Nếu câu trả lời khác nhau, đó là do **trọng số** đã
  thay đổi, không phải do prompt.
- **Danh tính, định dạng và phạm vi** thay đổi rất rõ. Đó là thế mạnh của tinh chỉnh.
- **Số liệu kỹ thuật** thì chưa chắc đúng. Một mô hình 1,5B học thuộc dữ kiện không
  ổn định và có thể "bịa" số. Vì vậy với dữ kiện, ta dùng **RAG** (Bài 2): tra cứu
  tài liệu tại thời điểm hỏi, và luôn đưa kèm nguồn.

### Bài tập

1. Đổi chữ ký trong `data/build_dataset.py` (biến `SIGN_VI`), chạy
   `python3 data/build_dataset.py`, rồi huấn luyện lại. Chữ ký mới có xuất hiện không?
2. Thử **2 epoch** rồi **6 epoch**. Loss thấp hơn có luôn tốt hơn không? Hỏi một câu
   ngoài phạm vi và xem mô hình còn trả lời tự nhiên không (học quá khớp — overfitting).
3. Thêm 5 câu hỏi về một chủ đề mới (ví dụ: chính sách đổi trả) và kiểm tra xem mô
   hình có trả lời được câu hỏi *diễn đạt khác* về chủ đề đó không.

## English

### What you will do

Take a small open model (**Qwen2.5-1.5B-Instruct**) and teach it to become
**Aurora**, the technical assistant of the fictional company Aurora Grid Systems,
in a few minutes on the RTX Spark's GPU. Then ask the original and the
fine-tuned model the same questions, side by side.

### Key ideas

- **LoRA** leaves the 1.5 billion base parameters frozen and trains small added
  matrices instead (about 1% of the parameters): fast, light on memory, and the
  base model stays intact.
- **Only the reply is learned.** Each example is a conversation; the loss is
  computed on the assistant's reply only (`train_lora.py`, `tokenize_examples`).
- **GGUF** is the file format Ollama and llama.cpp run. After training, the
  adapters are merged into the weights and converted with llama.cpp's converter.

### Steps

1. Open the **1 · Fine-tuning** tab.
2. Read the **training data**: identity, an answer format with a sign-off,
   polite refusals, and a few product facts. Source: `data/train.jsonl`,
   generated by `data/build_dataset.py`.
3. Click **Start fine-tuning** and watch the loss fall.
4. When it says "Done", use **Before vs after**. The sample questions are phrased
   differently from the training data (`data/eval.json`).

### What to notice

- Both models receive the **identical system prompt**, which literally says "You
  are Qwen". Any difference comes from the **weights**.
- **Identity, format and scope** change unmistakably — that is what
  fine-tuning is good at.
- **Facts** are unreliable: a 1.5B model memorises them poorly and may invent
  numbers. That is why facts belong in **RAG** (Hands-on 2), which looks them up
  at question time and cites the source.

### Exercises

1. Change the sign-off (`SIGN_VI` in `data/build_dataset.py`), rebuild the data
   with `python3 data/build_dataset.py`, retrain. Does the new sign-off appear?
2. Train for 2 epochs, then 6. Is a lower loss always better? Ask an off-topic
   question and look for overfitting.
3. Add five questions about a new topic and test a differently phrased question
   about it.

## How it runs

| Step | Where | What |
|---|---|---|
| train | NGC PyTorch container (`nvcr.io/nvidia/pytorch:25.11-py3` + `Dockerfile`) on the GPU | `train_lora.py`: tokenise with the chat template, LoRA r=16 on all projection layers, AdamW with warm-up + cosine decay |
| merge + convert | same container | `merge_and_unload()`, save safetensors, `convert_hf_to_gguf.py --outtype q8_0` (llama.cpp `v0.4.1`) |
| serve | host | `ollama create aurora-assistant -f output/Modelfile` |
| compare | workshop app | the same question and system prompt to `qwen2.5:1.5b-instruct` and `aurora-assistant` |

From a terminal, without the app:

```bash
hands-on-1-finetune/run_finetune.sh                    # epochs 5, lr 2e-4, rank 16
hands-on-1-finetune/run_finetune.sh --epochs 6 --rank 32
ollama run aurora-assistant "Bạn là ai?"
```

`setup.sh` builds the container, caches the base model (so the lab runs
offline) and trains once, so a ready model exists before the session.

Outputs land in `output/` (git-ignored): `merged/` (safetensors), `adapter/`
(the LoRA adapter alone, a few MB), the GGUF, `Modelfile`, `summary.json`.

### Troubleshooting

| Symptom | Fix |
|---|---|
| "training image … is missing" | run `./setup.sh` (it builds `workshop-finetune:latest`) |
| CUDA out of memory | the Spark's memory is shared with the models Ollama keeps loaded; stop the app, then `sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'` (from NVIDIA's DGX Spark playbooks) and retry |
| "ollama create failed" | see `output/ollama-create.log`; check `ollama list` works |
| the new model still says it is Qwen | train more epochs (4-6), or raise the learning rate to 3e-4 |
